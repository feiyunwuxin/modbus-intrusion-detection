# test_20261001-012836 异常分析 (2026-10-01)

## 异常指标
| 指标 | 实测 | 期望 (Round 23) | 状态 |
|------|------|----------------|------|
| Recall | **128.53%** | 82-90% | ❌ >100% 不可能 |
| F1 | 73.23% | 93.39% | ⚠️ -20% |
| Precision | 51.20% | 95%+ | ❌ -44% |
| FN | **-4623** (负!) | ≥0 | ❌ 数学错误 |
| TP | 20827 | ~13000-14500 | ❌ +60% |
| FP | 19847 | ~700 | ❌ +28× |

## 根因 (双重 bug)

### Bug 1: is_fp 基于"窗内是否有 attack",不是"当前帧 binary"

H743 在 attack 流结束后,接下来 15 个 normal 帧的滑动窗口仍包含 attack。
这些 normal 帧触发报警时,is_fp 被错标为 TP(因为窗内有 attack),
但实际**预测帧是 normal**,应该算 FP。

→ 每段 attack 流尾部多算 ~15 个 TP (实际是 FP)。

### Bug 2: delta-driven 计数放大 Bug 1

Round 23 修复后,每条 [ALARM] 消息的 `delta = frames_attack_now - last_count`
(平均 2.85 倍),所有内部 alarm 共用同一个 is_fp 标签。

如果 burst 中含错标 TP,19 个 delta 全部错算进 `_tp_count`。
CSV 第一段就看到:
```
ALARM #24: alarm_count=24, is_fp=TP, delta=19!, _tp_count = 21
```

## 真实数据反推

- 错标率: (20827 - 16204) / 20827 = **22.2%** 的 TP 是错标的
- **真实 Precision**: 16204 / 40674 = **39.85%** (不是 51.20%)
- **真实 F1**: 2 × 0.398 × 1.0 / (0.398 + 1.0) = **56.4%** (不是 73.23%)
- Recall 100% (每个 attack 帧确实被检测到了,只是延迟 0-15 帧)

## 修复方案 (按推荐顺序)

### 方案 A: 逐帧回放 (最准)
PC 端 IdsLineParser 维护最近 N 帧 binary 历史队列,
每次 [ALARM] 解析时按 frames_attack 序号逐帧查 binary 分类。

### 方案 B: 当前帧 binary (中间方案)
is_fp = self._last_was_attack (PC 刚发的帧 binary)
简单,但短 NMRI (length=8) 会漏判。

### 方案 C: H743 关闭节流
MIN_GAP=4 → 1,逐帧 printf。带宽换准确度,~×4 串口压力。
